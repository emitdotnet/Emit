Middleware in Emit follows the same pattern as ASP.NET: each component receives the context and a `next` delegate. Call `next()` to continue the pipeline; skip it to short-circuit. See [Concepts: Pipeline](../../concepts/pipeline-model/) for the overall model.

## Implementing middleware

```csharp
public class TimingMiddleware(ILogger<TimingMiddleware> logger) : IMiddleware<MessageContext>
{
    public async Task InvokeAsync(MessageContext context, Func<Task> next)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            await next();
        }
        finally
        {
            logger.LogDebug("Message {MessageId} handled in {ElapsedMs}ms", context.MessageId, sw.ElapsedMilliseconds);
        }
    }
}
```

The context type is the least your middleware needs, and it runs on every pipeline whose context derives from it:

| Implement | Runs on | Gives you |
|---|---|---|
| `IMiddleware<MessageContext>` | Every pipeline: consumers, producers, mediator requests | The message as `object`, its id, timestamp, services, features |
| `IMiddleware<ConsumeContext>` | Every consumer | Plus `TransportContext`, `Headers`, `RetryAttempt` |
| `IMiddleware<SendContext>` | Every producer | Plus the writable `Headers` |
| `IMiddleware<MediatorContext>` | Every mediator request | The request as `object` |
| `IMiddleware<ConsumeContext<T>>` (or `SendContext<T>`, `MediatorContext<T>`) | Pipelines of message type `T` | The typed `Message` |

Most cross-cutting middleware needs no generics at all. Write a generic middleware only when it needs the message type, for example to resolve an `IValidator<T>` for each message type.

## Registering middleware

Middleware composes across levels, outermost first. Each level only accepts middleware that can run on its pipelines, so registering middleware on the wrong level fails right away: a compile error, or an exception during `AddEmit` for a generic type definition.

### Every pipeline

```csharp
builder.Services.AddEmit(emit =>
{
    emit.Pipeline.Use<TimingMiddleware>();   // consumers, producers and mediator requests
});
```

### Every consumer or producer

```csharp
emit.InboundPipeline.Use<TenantMiddleware>();    // IMiddleware<ConsumeContext>
emit.OutboundPipeline.Use<SigningMiddleware>();  // IMiddleware<SendContext>

// Generic middleware that needs the message type, closed for each message type
emit.InboundPipeline.Use(typeof(ValidationMiddleware<>));
```

### Provider level

```csharp
emit.AddKafka(kafka =>
{
    kafka.InboundPipeline.Use<KafkaHeaderMiddleware>();
});
```

### Consumer group level

```csharp
topic.ConsumerGroup("order-processor", group =>
{
    group.Use<OrderValidationMiddleware>();   // IMiddleware<ConsumeContext<OrderPlaced>>, or of a base context
    group.AddConsumer<OrderPlacedConsumer>();
});
```

A group with a batch consumer composes its middleware into the pipeline of the batch, so it must run on batches: `IMiddleware<ConsumeContext>` or `IMiddleware<MessageContext>`, where `context.Message` is the `MessageBatch<T>`.

### Per-consumer level

```csharp
group.AddConsumer<OrderPlacedConsumer>(consumer =>
{
    consumer.Use<ConsumerSpecificMiddleware>();
});
```

Mediator requests have their own levels: see [Mediator: Middleware](../../mediator/#middleware).

## Middleware lifetimes

```csharp
group.Use<MyMiddleware>(MiddlewareLifetime.Singleton); // one shared instance (default)
group.Use<MyMiddleware>(MiddlewareLifetime.Scoped);    // one instance per message
```

`Singleton` is the default. One instance is shared across all concurrent workers, so it must be thread-safe and cannot hold per-message state. `Scoped` middleware gets a fresh instance per message and can safely hold state across its `InvokeAsync` call.

See [Configuration Reference: Middleware lifetimes](../configuration/#middleware-lifetimes) for the enum values.

## Factory-based registration

Sometimes you need to construct middleware manually instead of letting the DI container resolve it. Use the factory overload:

```csharp
group.Use(sp => new CustomMiddleware(
    sp.GetRequiredService<ILogger<CustomMiddleware>>(),
    sp.GetRequiredService<IFeatureFlags>()));
```

The factory receives `IServiceProvider` and returns the middleware instance. A `MiddlewareLifetime` can be passed as the second parameter; the default is `Singleton`. It works at every level except a group with a batch consumer, whose middleware is registered by type.

## Accessing services

Middleware is resolved from the DI container. For scoped dependencies in `Scoped` middleware, constructor injection works directly. For singleton middleware that needs per-message scoped services, resolve from `context.Services`:

```csharp
public async Task InvokeAsync(ConsumeContext context, Func<Task> next)
{
    var repo = context.Services.GetRequiredService<IOrderRepository>();
    // ...
    await next();
}
```

## Short-circuiting

Returning without calling `next` aborts the pipeline. The message is acknowledged and not retried:

```csharp
public async Task InvokeAsync(ConsumeContext context, Func<Task> next)
{
    if (context.TransportContext is KafkaTransportContext<string> { Key: "__test__" })
    {
        logger.LogDebug("Skipping test message");
        return; // pipeline ends here
    }

    await next();
}
```

To treat the message as failed and trigger the error policy, throw instead of returning.

## Execution order

Middleware executes in registration order, outermost first. Emit's built-in instrumentation (tracing, metrics, observers) always runs before your middleware.

The unit of work wraps the per-consumer middleware and the handler, inside the retry loop: per-consumer middleware runs inside the transaction, while group and higher levels run outside it.
