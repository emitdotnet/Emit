Emit traces every message from the code that produces it to every consumer that processes it, across the outbox and across services. A request that produces a message in your HTTP handler shows up in one trace with the message's delivery and processing, in any OpenTelemetry backend (Tempo, Jaeger, Zipkin, Datadog, and others). Spans follow the [OpenTelemetry messaging conventions](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/).

## Setup

```bash
dotnet add package Emit.OpenTelemetry
```

```csharp
builder.Services.AddOpenTelemetry()
    .WithTracing(tracing =>
    {
        tracing.AddEmitInstrumentation();
        tracing.AddOtlpExporter();  // or your preferred exporter
    });
```

`AddEmitInstrumentation` registers Emit's three activity sources: `Emit.Producer`, `Emit.Consumer` and `Emit.Mediator`.

## What a trace looks like

When you call `ProduceAsync`, Emit starts a `create` span and puts its trace context in the message headers. Everything that happens to the message afterwards joins that trace, whether it goes through the outbox or directly to the broker.

<Mermaid code={`flowchart TD
    H["POST /orders (your code)"] --> C["create orders"]
    C --> S["send orders"]
    C --> P1["process orders (consumer A)"]
    C --> P2["process orders (consumer B)"]
    P1 --> R["emit.retry"]`} />

| Span | What it covers |
|---|---|
| `create {topic}` | `ProduceAsync`: your outbound middleware, and writing the outbox entry or handing the message to the broker |
| `send {topic}` | The message going to the broker, until the broker acknowledges it. With the outbox, it happens later, on whichever node delivers the entry |
| `process {topic}` | One consumer processing the message, from receiving it to its outcome. Each consumer of the message, router included, has its own |
| `emit.retry` | One retry attempt, inside the `process` span |

**Batches.** A batch holds messages from different traces, so its `process` span links to the `create` span of each message instead of having one parent. You can navigate from the batch to each message's trace and back.

**Dead letters.** A dead letter continues the trace of the processing that failed: its `send` span is a child of that `process` span, and whoever consumes the dead letter joins the same trace.

<Mermaid code={`flowchart TD
    C["create orders"] --> P["process orders (failed)"]
    P --> D["send orders.dlt"]
    D --> PD["process orders.dlt"]`} />

**Mediator requests.** Each request gets a span named after the request type, and messages produced while handling it are created within that span.

## What the spans tell you

Spans carry the standard messaging attributes, such as the topic, partition, offset, consumer group and message id, so your backend can search and group them. Emit adds a few of its own: `emit.node.id` (the node that did the work), `emit.consumer` and `emit.consumer.type` (which consumer processed the message), `emit.route.key` (for a router) and `emit.retry.attempt` (on retry attempts).

A span is marked as an error when its work failed for good. A retry attempt that fails is an error on its own `emit.retry` span, but the `process` span is an error only when the message was finally dead-lettered or discarded. A message rejected by validation is not an error, and neither is a shutdown.

## Tracing options

```csharp
builder.Services.AddEmit(emit =>
{
    emit.ConfigureTracing(tracing =>
    {
        tracing.Configure(options =>
        {
            options.Enabled = true;               // set false to suppress all Emit spans
            options.CreateRootActivities = true;  // false = only spans that join an existing trace
            options.PropagateBaggage = true;      // propagate W3C baggage across message boundaries
            options.MaxBaggageSizeBytes = 8192;   // excess items are dropped with a warning
        });
    });
});
```

With `CreateRootActivities = false`, Emit never starts a new trace on its own: a message produced outside any span, or received without trace context, is not traced. Use it to keep background work out of your tracing backend.

## Adding your own tags

Implement `IActivityEnricher` to add application-specific tags:

```csharp
public class TenantActivityEnricher(ITenantContext tenant) : IActivityEnricher
{
    public void Enrich(Activity activity, EnrichmentContext context)
    {
        activity.SetTag("tenant.id", tenant.TenantId);
    }
}
```

```csharp
emit.ConfigureTracing(tracing =>
{
    tracing.AddEnricher<TenantActivityEnricher>();

    // or inline
    tracing.EnrichActivity((activity, context) => activity.SetTag("env", "production"));
});
```

Enrichers run on the `create` and `process` spans and on mediator requests. `EnrichmentContext.Phase` says which, as one of the `EnrichmentPhases` values: `Produce`, `Consume` or `Mediator`.
