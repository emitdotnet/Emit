---
title: Resilience
description: Circuit breakers and rate limiting for consumer groups.
---

Beyond retry policies, Emit provides two resilience mechanisms at the consumer group level: circuit breakers to stop hammering a downstream system that is clearly broken, and rate limiting to protect one that is struggling.

## Circuit breaker

A circuit breaker tracks failed handler attempts in a sliding window. When they exceed the threshold, it opens: the consumer group pauses and every message waits, retries included, until the pause duration elapses.

```csharp
topic.ConsumerGroup("order-processor", group =>
{
    group.CircuitBreaker(cb =>
    {
        cb.FailureThreshold(5);
        cb.SamplingWindow(TimeSpan.FromSeconds(60));
        cb.PauseDuration(TimeSpan.FromSeconds(30));
    });

    group.AddConsumer<OrderPlacedConsumer>();
});
```

| Option | Description |
|---|---|
| `FailureThreshold` | Number of failed attempts in the sampling window before the circuit opens |
| `SamplingWindow` | Rolling window of time in which failures are counted |
| `PauseDuration` | How long the consumer group is paused after the circuit opens |

### Trip conditions

By default, any exception trips the circuit. Narrow it to specific exception types:

```csharp
cb.TripOn<HttpRequestException>();
cb.TripOn<TimeoutException>();
```

Only the listed exception types increment the failure counter. Other exceptions pass through to the error policy without affecting the circuit.

### Counting with retries

Every failed attempt counts once, retries included. With `Retry(3)`, a message failing all 4 attempts counts 4 failures.

To keep messages from being dead-lettered during an outage, give the retry policy more retries than `FailureThreshold`. The circuit then opens while the message still has retries left, and its next attempt waits for the circuit instead of spending them.

### States

The circuit starts **Closed** (normal operation). When the failure threshold is exceeded, it moves to **Open**: the consumer group is paused, no new messages are fetched, and messages already fetched or waiting for a retry are held. The consumer keeps polling while paused, so it stays in the group however long the pause lasts. After `PauseDuration` elapses, the circuit enters **Half-open** and lets one attempt through at a time as the probe. If the probe succeeds, the circuit closes again. If it fails, the circuit reopens for another `PauseDuration`.

The circuit and your application pause the group independently, through [flow control](../../kafka/consumers/#flow-control): the group stays paused while either holds it. A half-open circuit lets its probe through only once your application has resumed the group.

Circuit breaker state transitions are tracked by the `emit.consumer.circuit_breaker.state_transitions` metric and the `emit.consumer.circuit_breaker.state` gauge.

## Rate limiter

Rate limiting throttles message processing to protect a downstream service:

```csharp
topic.ConsumerGroup("order-processor", group =>
{
    group.RateLimit(rl =>
    {
        rl.TokenBucket(permitsPerSecond: 100, burstSize: 100);
    });

    group.AddConsumer<OrderPlacedConsumer>();
});
```

Emit uses `System.Threading.RateLimiting` under the hood, so all four built-in algorithms are available:

| Algorithm | Method | Best for |
|---|---|---|
| Token bucket | `rl.TokenBucket(permitsPerSecond, burstSize)` | Smooth throughput with burst tolerance |
| Fixed window | `rl.FixedWindow(permits, window)` | Simple per-interval cap |
| Sliding window | `rl.SlidingWindow(permits, window, segmentsPerWindow)` | Smoother than fixed window; prevents edge-of-window bursts |

When a permit cannot be acquired immediately, the consumer waits. Wait duration is tracked by the `emit.consumer.rate_limit.wait_duration` metric.

## Ordering

When both are configured, the rate limiter throttles messages and the circuit breaker holds attempts. An open circuit holds each attempt before the handler runs, and the error policy only acts once an attempt has failed and no retry is left.
